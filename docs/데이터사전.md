# 데이터 사전 (1단계 기준)

> 실제 정의는 `server/schema.sql` 입니다 (새로 만들 때). 운영 중인 DB 는 `server/migrations/` 의 번호 파일을 한 번씩 실행합니다. 둘을 항상 함께 고칩니다.
> 규칙: 표·열 이름은 영문 snake_case, 상태·구분 값은 한국어, 날짜는 한국 시간 문자열(`YYYY-MM-DD`, `YYYY-MM-DD HH:MM:SS`).
> **현장 열:** 업무 표에는 모두 `project_id` 가 있고, 모든 조회·수정에 `project_id = ?` 조건을 건다.

## 1. 현장·설정

### projects — 현장(프로젝트)
| 열 | 설명 |
| --- | --- |
| id | 번호 (`P01`, `P` + 무작위 8자) |
| code | 짧은 코드(영문 소문자·숫자 3~20자, 유일). 직원 가입 링크 `staff.html?p=코드` 에 쓰임 |
| name | 현장 이름 (화면 상단에 표시) |
| kind | 유형: 아파트 / 오피스텔 / 상가 / 기타 (선택) |
| address, client | 주소, 시행·시공사 |
| status | `준비` / `진행` / `종료`. 종료 현장은 새 가입을 받지 않음 |
| start_date, end_date | 시작일·종료일 (비어 있을 수 있음) |
| money_label | `분양가` / `임대보증금` (이후 단계의 금액 명칭) |
| created_at | 만든 일시 |

### settings — 전체 공통 설정
`key`, `value`, `description`. 현재는 `텔레그램봇이름` 만 (모든 현장이 같은 봇). 옛 DB 에서 옮겨 온 `GPS허용거리m`·`예약중복기준` 행은 "새 현장의 기본값"으로 남아 있을 수 있음 (현장별 값이 있으면 그쪽이 우선).

### project_settings — 현장별 설정 (프로젝트 만들기·수정 화면에서 입력, `project.save` 의 `gpsDistance`·`dupRule`)
`(project_id, key)` → `value`. 키: `GPS허용거리m`(10~5000, 기본 200), `예약중복기준`(`뒤5자리` / `뒤5자리+성별`).
조회는 `settings` 위에 이 표를 덮어쓴 값 (`getSettings(env, projectId)`).

## 2. 사람·계정

### staff — 직원 (영업사원·팀장·본부장·기타 직군)
| 열 | 설명 |
| --- | --- |
| id | `S` + 무작위 |
| **project_id** | 소속 현장. **1인 1현장.** 현장 이동 = 이 값을 바꾸고 조직을 다시 지정, `logs` 에 기록 |
| name, nickname, phone | 성명, 예명, 휴대폰(숫자만). **phone 은 전체에서 유일**(사람당 1행) |
| job, head_id, team_id | 직군 이름, 본부·팀 번호(영업 직군만). 모두 **그 현장의** 조직 |
| grade, can_approve | 직급 `직원`/`팀장`/`본부장`, 가입 승인 권한 |
| status | `대기` / `활동` / `반려` / `퇴사` |
| pin_hash, fail_count | PIN(salt+SHA-256), 실패 횟수(5회 잠김) |
| device_key, device_change_request | 등록된 휴대폰, 기기 변경 요청 (휴대폰 1대 = 1명, 전체에서) |
| telegram_* | 텔레그램 연결 |

### payroll — 급여정보 (사람당 1행, 현장 열 없음)
주민번호(`rrn_enc`)·계좌번호(`account_enc`)는 AES-GCM 암호화, 은행·예금주·동의일시. 관리자 action 에서만 읽고 응답은 마스킹. 원문 열람은 `logs` 기록. 현장 이동해도 다시 받을 필요 없음.

### accounts — 로그인 계정
| 열 | 설명 |
| --- | --- |
| login_id, password_hash | 아이디(유일), 비밀번호(salt+SHA-256) |
| role | `관리자` / `보조관리자` / `계약담당` / `열람` / `데스크` / `방명록` |
| must_change_password, fail_count, active | 첫 로그인 변경 강제, 실패 횟수, 사용 여부 |
| email | 관리자 계정만 (비밀번호 초기화 인증 코드 수신) |
| allow_payroll | 보조관리자에게 급여정보 원문 보기를 허용 (기본 0) |
| allow_pay_confirm | 보조관리자에게 지급 확정을 허용 (기본 0, 2단계에서 사용) |

### account_projects — 계정이 접근할 수 있는 현장
`(account_id, project_id)`. 관리자는 행이 없다(전체). 보조관리자·계약담당·열람은 1개 이상, 데스크·방명록은 정확히 1개.

### sessions
`token`, `kind`(staff/account), `user_id`, `expires_at`. 현장은 세션에 저장하지 않고 **요청마다** 확인한다 (한 계정이 여러 창에서 서로 다른 현장을 볼 수 있고, 담당 현장 변경이 즉시 반영됨).

### password_resets
관리자 비밀번호 이메일 인증 초기화용 (코드 해시, 시도 횟수, 잠금).

## 3. 조직

### orgs — 직군·본부·팀 (현장마다 따로)
`id`, **project_id**, `kind`(직군/본부/팀), `name`, `parent_id`(팀의 소속 본부), `sort_order`, `active`. 새 현장에는 기본 직군(영업·홍보단·상담사·도우미·아르바이트)이 함께 만들어짐. `영업` 직군만 본부→팀을 선택하고 이름을 바꿀 수 없음.

## 4. 근태·방문

| 표 | 현장 열 | 설명 |
| --- | --- | --- |
| qr_issues | project_id (기본키 = 현장 + 날짜) | 그날의 출근 QR 과 기준 좌표 |
| attendance | project_id | 출근 기록. 유일 색인: 현장+날짜+직원, 현장+날짜+기기 (성공 기록만) |
| reservations | project_id | 방문 예약 (뒤 5자리, 방문예정일, 담당 직원, 상태 예정/방문/미방문/취소). 중복 판정은 같은 현장 안에서만. 담당 직원이 다른 현장으로 이동하면 오늘 이후 '예정' 건은 '취소'(메모에 사유), 지난·방문 완료 건은 그대로 남고 이름 뒤에 (타 현장 이전)이 붙음 |
| visits | project_id | 호출 기록 (화면 이름 '호출'. 방문 통계의 기준은 방명록) (kind 예약/지명/담당없음/방명록, 호출·확인 시각) |
| guestbook | project_id | 방명록 (고객 입력/데스크 입력, 담당 본부·팀·직원, 동의, 호출 연결) |
| tg_updates | — | 텔레그램 웹훅 중복 처리 방지 (현장과 무관) |

## 4-1. 근태 보정·용역관리 (2단계)

### attendance_adjust — 근태 보정 (원본 attendance 는 고치지 않음)
`id`, **project_id**, `staff_id`, `date`, `kind`(`인정` 1일 / `불인정` 0일 / `반일` 0.5일), `reason`, `created_by`, `created_at`. 유일: 현장+직원+날짜. 확정된 정산 기간의 날짜는 보정할 수 없다. 인정 근무일수 = 출근 성공(1일) 위에 보정을 덮어쓴 값.

### staff_pay — 개인별 지급 설정 (현장별, 적용 시작일 이력)
`project_id`, `staff_id`, `effective_from`(유일: 현장+직원+시작일), `daily_wage`(원, 정수), `cycle`(`주`/`월`), `daily_enabled`(일당 지급 대상), `fee_enabled`(판매수수료 대상 — 영업 직군이 기본, 5단계에서 사용), `pay_mode`(`3.3%` / `공제없음` / `업체일괄`), `supplier_id`(업체일괄일 때 지급 대상 업체), `withhold`(= `pay_mode='3.3%'` 일 때 1, 이전 열), `created_by`, `created_at`. 날짜 d 에 적용되는 설정 = `effective_from <= d` 중 가장 늦은 것.

### job_pay — 직군별 기본 지급 설정 (현장별, 적용 시작일 이력)
`staff_pay` 와 같은 항목(`job`, `effective_from`, `daily_wage`, `cycle`, `daily_enabled`, `fee_enabled`, `withhold`). 유일: 현장+직군+시작일. **적용 순서: 그 날짜에 직원 개인 설정이 있으면 개인 설정, 없으면 그 직원의 직군 기본 설정.** 다른 현장으로 이동한 직원은 직군 기본을 쓰지 않고 개인 설정만 본다(직군은 현장마다 다르므로).

### suppliers — 인력공급업체 (현장별)
`name`(현장 안에서 유일), `biz_no`, `bank`, `account_enc`(계좌번호, AES-GCM 암호화 — 화면에는 보내지 않고 이체 파일을 만들 때만 풀며 기록), `holder`, `contact`, `active`. 지급 설정이 `pay_mode='업체일괄'` 이면 이 업체를 가리킨다(`supplier_id`).

### pay_runs — 정산 회차 (현장 + 기간)
`project_id`, `kind`(지금은 `일급`), `title`, `cycle`, `period_from`, `period_to`, `status`(`작성`→`검토`→`확정`→`지급완료`), `memo`, `created_by/at`, `reviewed_at`, `confirmed_by/at`, `paid_at`. 확정 이후에는 고치거나 지울 수 없다.

### pay_items — 회차별 개인 명세
`run_id`, **project_id**, `staff_id`, `name`(그때 이름), `units`(반일 단위: 2 = 1일), `base_amount`(일급 합계), `adjust_amount`/`adjust_memo`(± 조정), `gross`(지급액 = 일급 합계 + 조정. **업체일괄이면 업체에 청구하는 공급가**), `pay_mode`·`supplier_id`·`supplier_name`(그때 업체 이름), `income_tax`(소득세 3%), `local_tax`(지방소득세 0.3%), `net`(개인 실지급액. 업체일괄은 0), `withhold`, `detail_json`(날짜별 내역: 날짜·단위·그날 일당·금액·구분). 유일: 회차+직원.
**계산 규칙(한 곳: `server/src/pay/calc.js`)**: 하루 금액 = 일당 × 단위 ÷ 2 (원 단위 절사), 세금은 지급액에서 각각 절사, 모든 금액은 정수.
**현장 이동과의 관계**: 명세의 `project_id` 는 일한 현장이다. 직원이 나중에 다른 현장으로 이동해도 이전 현장 기간의 명세는 이전 현장 회차에서 지급된다.

## 4-2. 설문·고객 통합 (3단계)

### surveys — 설문 (현장별)
`id`, **project_id**, `title`, `description`, `theme`(응답 화면 색), `status`(`작성`/`진행`/`마감`), `questions_json`(문항 목록 `{key, std, type, title, required, options:[{code,label}]}`), `consent_text`(개인정보 동의 문구, 현장·설문별), `version`. 공통 문항 은행은 표가 아니라 코드 상수(`server/src/survey/std.js`)이고, 공통 문항의 `key` 는 `STD_` 로 시작하며 보기 코드가 고정이다(현장 간 비교용). 직접 만든 문항 key 는 `Q` + 영숫자.

### survey_links — 배포 링크
`code`(6자 기본키), **project_id**, `survey_id`, `kind`(`본부`/`팀`/`직원`/`기타`), `head_id`, `team_id`, `person_id`, `label`, `active`. 직원 개인 링크는 설문당 1개(유일 색인).

### responses — 응답 원장
`id`, **project_id**, `survey_id`, `link_code`, `head_id`/`team_id`/`person_id`(링크에서 복사), `submitted_at`, `consent_pi`, `consent_mkt`, `phone_hash`(동의한 응답만), `nonce`(같은 제출 중복 방지, 설문+nonce 유일), `answers_json`(이름·전화번호는 들어가지 않음).

### response_answers — 세로형 답변
`response_id`, **project_id**, `survey_id`, `q_key`, `value_code`, `value_text`. 공통 문항 현장 비교·통계용.

### response_pii — 응답자 개인정보 (동의한 응답만)
`response_id`, **project_id**, `name`, `phone_enc`(AES-GCM). 동의하지 않은 응답은 행이 없다. 현장 종료 후 6개월이 지나면 `survey.purgePii` 로 일괄 파기(응답 통계는 남음).

### 고객 통합 키
`phone_hash` = 전화번호 숫자만 + salt 의 SHA-256 (`util.js phoneHash`). `responses.phone_hash`, `guestbook.phone_hash`(방명록은 개인정보 제공 동의 건만, 기존 행은 고객 목록을 열 때 채움)가 같으면 같은 고객이다. 고객 목록(`customer.list`)은 표를 따로 두지 않고 이 두 표를 그때그때 묶는다. 계약·TM·상담은 해당 기능이 생기면 같은 키로 잇는다.

## 5. 기록

### logs
`at`, `user`, `action`, `target`, `content`, **project_id**(현장과 무관한 일은 빈 값). 기록 대상: 직원 승인·반려·수정·퇴사·현장 이동, PIN 초기화, 기기 변경 승인, **급여정보 원문 열람**, 설정 변경, 조직·계정·현장 생성/수정, QR 발급, 방명록 등록/수정/삭제/**내보내기**.
