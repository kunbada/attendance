# 위뉴 통합 프로젝트 관리 앱 — 구성안 (v0.1, 2026-10-20)

> 이 문서는 채팅에서 정한 **설계 기준**이다. 실제 개발은 Claude Code에서 이 폴더(`D:\mycode\통합프로젝트관리앱`)를 그대로 열어 진행한다.
> 개발 규칙은 루트 `CLAUDE.md`, 각 앱의 세부 규칙은 각 폴더의 `CLAUDE.md`를 따른다.
> 이 문서에 없는 기능은 만들지 않는다. 바꿔야 하면 이 문서를 먼저 고친다.

## 1. 현재 상태 (2026-10-20 폴더 점검 결과)

| 앱 | 화면 | 서버·DB | 상태 | 프로젝트 개념 |
|---|---|---|---|---|
| **근태관리** | `web/` staff·desk·guest·admin.html (GitHub Pages `kunbada.github.io/attendance/`) | **Cloudflare Worker + D1** (`attendance-api`, DB `attendance`) | 4단계까지 완료, 배포됨. 텔레그램·이메일 연동 | **없음** (한 현장 = 한 DB, `settings.현장명`) |
| **분양계약관리** | 단일 HTML(오프라인 우선, IndexedDB) | Apps Script + 구글시트 (현장마다 시트 자동 생성) | 기능 대부분 완료. **실제 Apps Script 배포는 미검증** | 있음 (`pk` 현장키) |
| **설문관리** | Apps Script HTML(Admin·Survey) + GitHub Pages iframe 래퍼 | Apps Script + 구글시트 | **실제 환경 실행 테스트 전** | 있음 (Projects 시트) |

판단:
- 근태관리가 가장 성숙하고(인증·역할·세션·암호화·테스트), 이미 빠른 DB(D1)를 쓰고 있다 → **통합 서버의 뼈대로 삼는다.**
- 계약·설문은 아직 구글 서버로 실제 운영 전이다 → **지금이 서버를 D1로 옮기는 가장 싼 시점**이다.
- 구글시트는 속도(한 요청 1~3초)·동시성·용량 면에서 통합 데이터 처리에 맞지 않는다. 엑셀이 필요하면 "내보내기"로 해결한다.

## 2. 목표 구조 — "하나의 서버·하나의 DB·하나의 로그인, 화면은 용도별"

```
                         ┌───────────────────────────────┐
                         │  통합 서버 (Cloudflare Worker)  │
   통합관리(hub) ───────▶ │  action 라우팅 · 권한 · 프로젝트 범위 │
   직원앱(staff) ───────▶ │                               │──▶  D1 데이터베이스 1개
   데스크·방명록 ────────▶ │  core / 근태 / 방문 / 설문 /     │     (모든 표에 project_id)
   설문 응답 화면 ───────▶ │  계약동기화 / 지급 / 레포트       │
   계약관리(오프라인) ───▶ │                               │──▶  텔레그램 · 이메일(Resend)
                         └───────────────────────────────┘
```

| 화면 | 사용자 | 기존 앱과 관계 |
|---|---|---|
| **통합관리 (hub)** — 신규 | 관리자·보조관리자 (PC) | 근태 `admin.html` 기능을 흡수하고 고객관리(설문·방문 등)·계약관리·용역관리 등을 추가(메뉴 구성은 6장). **1단계에서 admin.html 기능을 전부 hub로 옮겼고**, admin.html 은 hub로 자동 이동하는 안내 페이지만 남김(6단계에서 삭제) |
| **직원앱** `staff.html` | 영업사원·팀장·본부장 (휴대폰) | **그대로 유지**. 프로젝트(현장)를 hub에서 받아옴. 내 설문 링크/QR 추가 |
| **데스크·방명록** `desk.html`, `guest.html` | 데스크·방명록 태블릿 | 그대로 유지. 계정이 특정 프로젝트에 묶임 |
| **설문 응답 화면** — 정적 페이지로 이전 | 고객(비로그인) | 기존 `Survey.html` 화면·흐름을 옮김. 구글 안내 띠·iframe 래퍼가 사라짐 |
| **계약관리** | 관리자·보조관리자·현장 계약담당 (PC) | 화면·오프라인 동작 그대로. **동기화 서버만 Apps Script → 통합 서버로 교체** |

"1개의 앱"의 의미: 서버·DB·계정·프로젝트 목록이 하나이고, hub 메뉴에서 각 화면으로 같은 로그인으로 들어간다. 화면을 억지로 한 HTML에 합치지 않는다(휴대폰용·태블릿용·오프라인용은 성격이 달라서 분리가 유지보수에 유리).

### 2-1. 서버 선택 이유
- 기존 `attendance-api` Worker와 D1을 **확장**한다 (이름은 당분간 유지 → 직원앱 주소·홈화면 바로가기를 바꾸지 않아도 됨).
- D1은 SQLite라 계약×직원×근태를 한 번의 SQL로 합쳐 수수료·일당을 계산할 수 있다. 시트 여러 개를 오가는 방식보다 빠르고 단순하다.
- 비용: 무료 플랜 한도는 DB당 500MB, 하루 읽기 500만 행·쓰기 10만 행, **요청 1번에 쿼리 50개**. 지급 산출·대시보드처럼 한 번에 많이 읽는 기능이 생기므로 **운영 시작 시 Workers Paid(월 $5) 전환을 권장**(DB 10GB, 요청당 쿼리 1,000개). 무료로 시작하되 한도에 걸리면 바로 전환.

## 4. 사용자와 권한

### 4-1. 역할

| 역할 | 로그인 | 범위 | 비고 |
|---|---|---|---|
| **관리자** | 아이디+비밀번호 | 전체 프로젝트 | 계정 생성, 급여정보 원문 보기, 지급 **확정**, 규칙 변경 |
| **보조관리자** | 아이디+비밀번호 | **지정된 프로젝트만** | 인력·근태·설문·계약 데이터 관리, 지급 산출(확정은 관리자). 급여정보는 마스킹만 (관리자가 계정별로 허용 가능) |
| **계약담당** (선택) | 아이디+비밀번호 | 지정 프로젝트 | 계약관리 화면 입력·수정만 (기존 계약앱 `write`) |
| **열람** (선택) | 아이디+비밀번호 | 지정 프로젝트 | 레포트·대시보드 조회만 (시행사 보고용 등) |
| **데스크 / 방명록** | 아이디+비밀번호 | 1개 프로젝트에 고정 | 기존 그대로 |
| **본부장 / 팀장** | 휴대폰+PIN (직원앱) | 소속 프로젝트·소속 조직 | 기존 그대로 + 소속 조직 실적·지급내역 조회 |
| **영업사원** | 휴대폰+PIN (직원앱) | 본인 | 출근·예약·내 설문링크·**내 지급내역(일당·수수료)** 조회 |

- 계약앱의 `admin / write / read` 권한은 위 역할로 대체한다 (관리자·보조관리자=admin, 계약담당=write, 열람=read).
- 권한 확인은 **항상 서버에서**: 세션 → 역할 → **프로젝트 범위** → (직원이면) deviceKey. 화면에서 버튼을 숨기는 것은 편의일 뿐이다.
- 상세 표는 1단계에서 `docs/권한표.md` 로 작성.

### 4-2. 프로젝트 범위 처리 (가장 중요한 공통 규칙)
- 모든 업무 표에 `project_id` 를 둔다. 모든 조회·수정 쿼리는 `WHERE project_id = ?` 를 서버 공통 함수로 강제한다.
- 계정은 `account_projects(account_id, project_id)` 로 범위를 갖는다 (관리자는 전체).
- 직원앱: **영업사원은 한 번에 1개 현장에만 소속**된다 (결정 2026-10-20). 가입 링크에 현장 코드가 들어 있어(`staff.html?p=코드#signup`) 가입과 동시에 소속이 정해지고, 로그인하면 그 현장으로 바로 들어간다. 현장 이동은 관리자가 소속을 바꾸고 이력(`logs`)을 남긴다.

## 5. 데이터 구조 (D1) — 핵심 표

> 실제 열 정의는 1단계에서 `docs/데이터사전.md` 와 `server/schema.sql` 로 확정한다. 기존 근태 규칙 유지: 영문 snake_case, 상태값은 한국어, 날짜는 KST 문자열, 스키마 변경은 `migrations/` 번호 파일(기존 데이터 삭제 금지).

### 5-1. 공통 (core)
| 표 | 내용 |
|---|---|
| `projects` | id, code(짧은 코드, 링크용), name, kind(APT/오피스텔/상가/임대…), address, client(시행·시공사), status(준비/진행/종료), start_date, end_date, money_label('분양가'/'임대보증금'), created_at |
| `project_settings` | (project_id, key) → value. 기존 근태 `settings` 를 프로젝트별로 (GPS허용거리, 예약중복기준 등) |
| `staff` | 기존 표 + **`project_id`** (1인 1현장). **사람의 고유 기준은 휴대폰 번호**(전체에서 유일, 사람당 1행, 내부 번호 `S…`는 가입 때 발급). 주민번호는 암호화 저장하며 구분 키로 쓰지 않는다. 현장 이동 = project_id 변경 + 조직 재지정 + 아직 방문 전 예약 취소 + 로그. 다른 현장에 이미 가입된 번호는 가입 때 "○○ 현장에 가입되어 있습니다" 로 안내 |
| `payroll` | 급여정보(암호화) — 기존 그대로 (사람당 1행이므로 현장 이동해도 재입력 불필요) |
| `job_pay` | **직군별 기본 지급 설정**: project_id, 직군, 일당, 지급주기, 일당 지급 대상, 판매수수료 대상(영업 직군이 기본), 3.3% 공제, 적용 시작일(이력). **개인 설정(`staff_pay`)이 없는 직원에게 적용되고, 개인 설정이 있으면 개인 설정이 우선** (2026-10-21) |
| `staff_pay` | 개인별 지급 설정: staff_id, **project_id(현장별 단가·주기)**, 일당(원), 지급주기(주/월), 공제(기본 3.3%), 적용 시작일 — 변경 이력 보존. 현장 이동 후에는 새 현장 단가를 따로 입력 |
| `orgs` | 기존 + project_id (본부·팀·직군은 현장마다 다름) |
| `accounts` / `account_projects` | 관리자·보조관리자·계약담당·열람·데스크·방명록 + 담당 프로젝트. 보조관리자별 `allow_payroll`(급여 원문 보기), `allow_pay_confirm`(지급 확정) 허용 열 |
| `sessions` | 기존 그대로. **현장은 세션에 저장하지 않고 요청마다 `projectId` 로 받아** 계정의 접근 범위를 매번 확인한다 (여러 창에서 다른 현장을 볼 수 있고, 담당 현장 변경이 바로 반영됨) — 1단계에서 확정 |
| `logs` | 기존 + project_id. 급여정보 열람·지급 확정·규칙 변경·개인정보 내보내기는 반드시 기록 |
| `customers_key` (선택, 6단계) | 전화번호 해시 기준 고객 연결용 (설문↔방명록↔계약 퍼널 분석) |

### 5-2. 근태·방문 (기존 표에 `project_id` 추가)
`qr_issues`(PK → project_id+date), `attendance`, `reservations`, `visits`, `guestbook` — 유일 색인도 project_id 를 포함하도록 변경.
신규: `attendance_adjust` — 관리자 보정(인정/불인정/반일, 사유, 처리자). 일당 계산은 **원본 근태 + 보정**으로 한다 (원본은 고치지 않음).

### 5-4. 계약 (계약앱 동기화 대상)
- 계약앱은 컬렉션(units, contracts, pre, locks, deposits, settings, templates) 단위로 레코드를 주고받는다. 이 구조를 **그대로 받는 표**를 둔다:
  `ct_records(project_id, col, id, rev, updated_at, updated_by, deleted, json)` + `ct_rev(project_id, col, rev)`.
- hub의 레포트·수수료 계산은 SQLite `json_extract` 로 읽고, 자주 쓰는 항목(동호, 상태, 계약일, 담당자, 금액)은 **생성 열 + 색인**으로 빠르게 만든다.
- 이 방식이면 계약앱 쪽 코드는 서버 주소와 로그인만 바꾸면 되고, 기존 "바뀐 필드만 전송·필드 단위 병합·이중계약/중복입금 거절" 규칙을 서버에서 그대로 재구현한다.
- **담당자 연결**: 지금 계약의 `team`, `staff` 는 글자다 → `staffId`(project_members 연결) 필드를 추가하고, 기존 글자는 hub의 "담당자 매칭" 화면에서 일괄 연결한다. 수수료는 `staffId` 가 있는 계약만 계산된다.

### 5-5. 용역관리 (일급·판매수수료)
| 표 | 내용 |
|---|---|
| (일당 단가) | **개인별** — 위 `staff_pay`. 가입 승인 시 직군 기본값(`project_settings`)을 채워 주고 관리자가 개인별로 수정 |
| `fee_rules` | **정액제**. project_id, 적용범위(기본 / 타입 / 동 / 동호 목록), **직원 금액 · 팀장 금액 · 본부장 금액**, **적용 기간(시작일~종료일, 계약일 기준 — 판매 시점/차수마다 금액이 달라질 수 있음)**. 같은 계약에 여러 규칙이 맞으면 **동호 > 동 > 타입 > 기본** 순으로 하나만 적용 |

**현장 이동과 정산 (확정 2026-10-20)**: 실적은 **발생한 현장에 남고, 그 현장의 정산 회차에서 지급**한다. 정산 회차는 `현장 + 기간` 단위이고 대상은 "그 기간에 그 현장에서 출근 기록이 있는 사람"이다(현재 소속과 무관). 그래서 정산 전에 다른 현장으로 이동해도 이전 현장 회차에는 이전 현장 근무일이, 현재 현장 회차에는 이동 후 근무일이 각각 들어간다. 수수료도 계약 당시 담당자·조직 기준이라 이전 현장 계약분은 이전 현장 정산에 들어간다. 사람당 급여정보(주민번호·계좌)는 하나라 이체 파일은 사람별로 현장 구분 없이 합산할 수 있으나, 현장별 지급 내역서는 따로 낸다. 현장 이동 때 관리자 화면에 "이전 현장에 남는 정산 전 실적"을 보여 준다(이번 달 출근일수 등).

**지급 방식 (확정 2026-10-21)**: 직원·직군 지급 설정에서 ① 개인에게 **3.3% 공제 후 지급**, ② **공제 없이 개인 지급**, ③ **인력공급업체 일괄지급** 중 선택한다. ③은 인력공급업체(현장별 등록: 상호·사업자번호·입금계좌)에 용역비를 묶어 주는 방식으로, **공급가 = 일당 × 출근일수(근태 보정 반영)**, **부가세는 별도(업체별 공급가 합계의 10%, 원 단위 절사)**, 업체 지급액 = 공급가 + 부가세. 이 경우 개인 3.3% 공제와 개인 지급은 없고(직원앱 '내 지급내역'에도 나오지 않음), 정산 화면과 이체 파일에 업체 단위로 한 건씩 나온다. 같은 정산 회차 안에 개인 지급분과 업체 일괄분이 함께 들어간다.

**일급 정산 운영 규칙 (2단계 구현)**: 회차는 `현장 + 기간(주 7일 이내 / 월 같은 달)`. 대상 = 기간 안에 그 현장에서 출근(또는 보정 인정)이 있고, 개인 지급 설정이 **일급 대상 + 같은 주기**인 사람. 설정이 없거나 주기가 다르면 이유와 함께 "포함되지 않은 사람"으로 보여 준다. 같은 기간이 겹치는 다른 회차에 이미 들어간 사람은 중복 지급을 막으려고 제외한다. 확정 직전에 근태·설정이 바뀌었는지 다시 계산해 비교하고 달라졌으면 확정을 거부한다. 확정·지급완료·이체 파일은 관리자 또는 계정별 허용을 받은 보조관리자만 한다.

**일당 계산** (결정 2026-10-20): 정산 회차를 만들 때 주기(주/월)와 기간을 고르면, 그 주기로 설정된 직원만 대상이 된다.
`지급액 = 인정 출근일수 × 개인 일당`, `공제 = 지급액 × 3.3%`(원 단위 절사, 소득세 3%·지방세 0.3% 각각 계산해 표시), `실지급액 = 지급액 − 공제`. 인정 출근일 = 출근 성공 + 보정(인정) − 보정(불인정).

**수수료 계산** (결정 2026-10-20): 계약 1건마다 적용 규칙의 금액을 **담당 직원 · 그 직원의 팀장 · 본부장**에게 각각 발생시킨다 (계약 당시 조직 기준으로 기록). 공제 3.3% 동일.

- **팀장·본부장 직접 계약** (확정): 본인이 **직원 몫 + 본인 직급 몫**을 모두 받는다. 상위 직급 몫은 상위자에게 정상 발생 (예: 팀장이 계약 → 팀장에게 직원 몫+팀장 몫, 본부장에게 본부장 몫). 본부장이 직접 계약하면 본부장에게 직원 몫+본부장 몫, 팀장 몫은 발생하지 않음(팀 소속이 없으므로).
- **공동판매 불가** (확정): 계약 1건의 담당자는 1명. 계약앱 `staffId` 는 한 명만 지정 가능하고 서버도 1명만 허용한다.

- **지급 시점** (확정): 계약금 **완납 후** 지급. 계약앱 수납 데이터(`payState(동호,'계약금')` = 완납)를 기준으로, 정산 기간 안에 완납된 계약만 대상.
- **해약 처리** (확정): 이미 지급한 수수료는 **환수** 또는 **해당 세대 재판매로 대체**.
  - 해약되면 `fee_ledger` 에 '환수 대기' 줄을 만든다(아직 차감하지 않음).
  - 관리자가 건별로 선택: [환수] → 다음 정산에서 차감 / [재판매 대체] → 그 세대가 다시 계약되면 환수 대기를 취소하고, 재계약분 수수료는 이미 지급한 것으로 보아 새로 발생시키지 않음(이중 지급 방지).
  - (확정) 재판매 대체는 **원래 담당 직원이 재판매한 경우에만** 인정. **다른 직원이 재판매하면 원 담당자는 환수, 새 담당자에게 정상 지급.**
  - (확정) 재판매 대기 기한은 **해약일로부터 3개월**. 기한까지 재계약이 없으면 자동으로 환수로 전환해 다음 정산에서 차감. 기한은 `project_settings` 에서 현장별로 바꿀 수 있게 한다(기본 3개월).
| `pay_runs` | 정산 회차: project_id, 구분(일당/수수료), 기간, 상태(작성→검토→확정→지급완료), 작성자, 확정자, 확정일 |
| `pay_items` | 회차별 개인 명세: person_id, 근거 건수(출근일·계약건), 금액, 공제(3.3% 등), 실지급액, 메모 |
| `fee_ledger` | 수수료 원장: 계약 1건마다 발생 / 지급 / **해약 환수(마이너스)** 를 줄로 쌓음 → 다음 정산에서 자동 차감 |

- **확정된 회차는 수정 불가** (정정은 다음 회차에 조정 줄로). 이체용 파일(은행·계좌·금액, 엑셀) 내보내기는 관리자만, 로그 기록.

### 5-6. 고객 통합과 향후 데이터 (고객관리 TM·상담, 출납관리) — 개략
- **한 고객 = 전화번호 해시(`phone_hash`) + 현장**. 설문·방명록(방문)·TM·상담·계약에서 같은 번호를 이 키로 연결한다(동의한 건만, 원문 번호는 암호화).
- 향후 표(요구사항 확정 후 설계): `tm_customers`(TM 인바운드), `consult_records`(상담석 상담 결과), `cash_entries`(출납: 일자·구분 현금/카드/계좌·항목·금액·증빙·작성자). 모두 `project_id` 포함.
- 데이터통합관리는 위 표를 읽는 조회 전용 화면이라, 새 데이터가 추가돼도 연결 키만 맞으면 확장된다.

| **설정** (관리자) | | 공통 설정(텔레그램 봇 등), 계정·권한·담당 프로젝트, 공통 문항 은행, 용역비 규칙 기본값 | ✅ 일부 |

- 기존 '레포트' 메뉴는 따로 두지 않는다. 보고서는 **각 메뉴에서 해당 데이터의 보고서**를 내고, 여러 데이터를 합친 보고서는 **고객관리 > 데이터통합관리**와 **홈**에서 낸다.
- 역할과의 관계: 계약담당 → 계약관리만, 열람(시행사 등) → 홈·데이터통합관리 조회만, 보조관리자 → 담당 현장의 각 메뉴(용역비 확정·급여 원문은 계정별 허용).

## 7. 설문 공통 문항 (데이터 분석용 표준) — 초안

원칙: 공통 문항은 **key와 보기 코드가 고정**된다. 화면에 보이는 문구는 현장마다 다듬어도 되지만 코드는 바꾸지 않는다 → 프로젝트가 달라도 같은 기준으로 합산·비교 가능. 보기 목록을 바꿔야 하면 `version` 을 올린다.

| 구분 | key | 문항 | 보기(코드) |
|---|---|---|---|
| **필수** | `STD_CONSENT_PI` | 개인정보 수집·이용 동의 | Y / N (N이면 이름·전화번호 저장 안 함, 답변은 익명 통계로만) |
| **필수** | `STD_INTENT` | 분양(계약) 의향 | 5 적극 있음 / 4 있음 / 3 고민 중 / 2 낮음 / 1 없음 |
| 권장 | `STD_CONSENT_MKT` | 분양 정보 안내(마케팅) 수신 동의 | Y / N |
| 권장 | `STD_NAME` · `STD_PHONE` | 성함 · 연락처 | (동의 시만 저장, 전화번호는 암호화+해시) |
| 권장 | `STD_GENDER` | 성별 | M / F |
| 권장 | `STD_AGE` | 연령대 | 20 / 30 / 40 / 50 / 60 (이상) |
| 권장 | `STD_REGION` | 거주지 | 시·군·구 선택 (행정구역 코드) |
| 권장 | `STD_HOUSING` | 현재 주거형태 | 자가 / 전세 / 월세 / 기타 |
| 권장 | `STD_HOUSES` | 주택 보유 | 무주택 / 1주택 / 2주택 이상 |
| 권장 | `STD_PURPOSE` | 구입 목적 | 실거주 / 투자 / 실거주+투자 |
| 권장 | `STD_TYPE` | 관심 타입 | 현장의 타입 목록(계약앱 units 의 type 에서 자동 생성) |
| 권장 | `STD_BUDGET` | 예상 자금 | 구간 코드 (현장 규모에 맞게 구간만 조정) |
| 권장 | `STD_TIMING` | 구입 시기 | 즉시 / 6개월 내 / 1년 내 / 미정 |
| 권장 | `STD_SOURCE` | 인지 경로 | 현수막 / 지인 / 영업사원 / 온라인 / 문자 / 기타 |
| 권장 | `STD_SUBSCR` | 청약통장 보유 | 있음 / 없음 |

- 현장 고유 문항은 자유롭게 추가 (key 자동 발급).
- 응답 화면의 개인정보 동의 문구·보유기간은 **운영 전 회사(법무) 확정 필요** — 임시 문구로 개발.
- 퍼널 분석: 동의한 응답은 `phone_hash` 로 방명록·방문·계약과 연결 → "설문에서 의향 4~5점 → 실제 방문 → 계약" 전환율을 현장·팀·직원별로 산출 (6단계).

## 8. 속도와 유지관리 원칙

1. **계약앱은 오프라인 우선 유지**: 화면은 로컬 IndexedDB로 즉시 동작, 서버와는 변경분만 주고받음(기존 rev 방식).
2. **hub는 필요한 만큼만 조회**: 목록은 페이지 단위, 기간·프로젝트 필터 필수. 마스터 데이터(프로젝트·조직·직원 목록)는 버전값을 두고 바뀔 때만 다시 받음.
3. **대시보드는 집계 표 사용**: `daily_stats(project_id, date, 지표…)` 를 쓰기 시점 또는 매일 밤 예약 작업(Cron Trigger)으로 갱신 → 화면은 집계 표만 읽음 (D1 읽기 한도·속도 모두 유리).
4. **색인**: 모든 업무 표는 `(project_id, 날짜)` 또는 `(project_id, 사람)` 순 색인.
5. **백업**: D1 자체 복원 기능(Time Travel) + 주 1회 `wrangler d1 export` 를 `private/` 에 보관 + 계약앱의 로컬 폴더 백업 유지.
6. **기술 규칙**: 프레임워크·번들러·TypeScript 없음, 순수 HTML/CSS/JS. 화면 라이브러리는 CDN 버전 고정(근태·hub), 계약앱만 인라인(오프라인). 서버는 순수 JS ES 모듈.
7. 한 파일이 길어지면 기능별로 나눈다. 서버는 `src/<모듈>/` 단위.
